学 SQL 注入之前，先把「一次 HTTP 请求到数据库」这条路走通。不理解这条路，注入就只是背 payload。

## 网络构成

```text
浏览器 --HTTP请求--> Web服务器(80) --> 应用代码 --> 数据库驱动 --> 数据库
查询结果集 --> 应用拼接响应 --> HTML渲染
```

逐层看各自在干什么：

| 层 | 职责 |
| --- | --- |
| **浏览器** | 用户填表单、点连接、发请求。所有来自外界、不可信的数据都来自这里产生 |
| **Web 服务器**（Apache/Nginx） | 接收网络请求，解析 HTTP 协议头，根据路由规则把请求交给对应的后端处理引擎 |
| **应用层**（PHP/JAVA/Python/GO） | 业务逻辑所在。从请求中提取参数，构造 SQL 命令，调用数据库客户端接口，并将取回的数据渲染进响应包 |
| **数据库驱动/连接层**（PDO/mysqli） | 负责应用与数据库之间的网络通信，序列化 SQL 文本或参数协议，传输结果集 |
| **数据库引擎**（MySQL） | 词法分析、语法解析，执行对应指令，读写磁盘数据并返回表数据 |

## 两种语言，一个翻译

这里有个关键错位：

- **浏览器说的是 HTTP/HTML**：请求头、表单字段、DOM 树、cookie、json。
- **数据库只认 SQL 语句。**

中间夹着的**应用代码就是翻译**。翻译分两个方向：

**进站翻译**——从 HTTP 请求里取出参数（`KEY=张`），组装成数据库能读懂的 SQL：

```sql
'SELECT ... WHERE name LIKE '%张%''
```

**出站翻译**——把数据库返回的二维表结果集（row），拼接成浏览器能渲染的 HTML 标签或前端能解析的 JSON 字符串。

## 注入就发生在这里

SQL 注入的本质，是**翻译在把用户输入拼接进 SQL 的那一刻，用户输入就变成了指令本身**。

数据库分不出这是正常的数据还是恶意指令——对它来说，收到的就是一条合法的 SQL。

所以防注入的思路也从这里来：要么别让用户输入碰 SQL 语句（预编译/参数化查询），要么在翻译之前就把输入按「数据」而不是「代码」处理（转义、白名单）。

理解了这条链路，后面看日志、读报错、判断注入点在哪一层，都有了一个固定的坐标系。
